README

A guide to AWS Trainium and Inferentia chips and the software that runs on them.

AWS builds two families of machine learning chips. Inferentia and Inferentia2 are designed for inference: running a trained model. Trainium, Trainium2, and Trainium3 support both training and inference. AWS calls each chip a Neuron device. An EC2 instance such as Trn2 provides the host CPU, host memory, and one or more of those devices.

From PyTorch to a chip#

  1. Choose a software path. On Trn2 or Trn3, TorchNeuron lets supported PyTorch code use the neuron device. The same entry links to examples for Hugging Face inference and fine-tuning. For serving a supported language model behind an API, start with vLLM Neuron. See the Neuron SDK for other workloads and older instance families.
  2. Compile and run. The compiler turns operations into a NEFF, the executable that the runtime loads and runs on the device.
  3. Follow the data. A modern NeuronCore brings small blocks of data called tiles from device memory into a fast scratchpad, SBUF. The Tensor Engine reads those tiles for matrix multiplication and accumulates results in PSUM. The compiler handles these transfers for framework code. When you write a custom NKI kernel, you can control them directly.

/device-hardware/collective-communication-engine

What is the Collective Communication Engine?CCE

The Collective Communication Engine (CCE) uses dedicated CC-Cores to handle collectives. These are operations in which a group of NeuronCores exchange or combine data, such as all-reduce, all-gather, reduce-scatter and all-to-all.

Dedicated hardware lets communication overlap with computation. For example, each replica in data-parallel training computes gradients for its batch. CC-Cores can combine the gradients for layers that have finished while the Tensor, Vector, and Scalar engines work on other layers.

If computation needs the result of a collective, it still has to wait for communication to finish.

CC-Cores drive traffic over NeuronLink within a scale-up domain. A domain can span multiple servers in an UltraServer. Across scale-up domains, collectives use EFA.

Counts per chip:

ChipCC-Cores
Trainium / Inferentia26
Trainium216 in the chip architecture, 20 in the NKI guide
Trainium316 in the chip architecture, 20 in the NKI guide

You do not program CC-Cores directly in normal use. Collectives are invoked through frameworks and libraries such as TorchNeuron and NxD Inference, and executed by the Neuron runtime. NKI kernels on Trn2 and Trn3 can request collective operations through nki.collectives. NKI collectives reference

To measure what the hardware actually achieves, use nccom-test, the Neuron equivalent of NCCL's benchmark tools.

What is the Descriptor Generation Engine?DGE

The Descriptor Generation Engine (DGE) is dedicated hardware, introduced in NeuronCore-v3, that generates DMA descriptors on demand. Each NeuronCore-v3 has two DGE instances.

A DMA descriptor tells a DMA engine what to move. It records where to read, where to write, how much data to copy, and how far to step between elements. A kernel that processes data in tiles can need many descriptors. Before v3, Neuron generated them in two ways.

  • Static generation. The host computed every descriptor when loading the NEFF, and stored them all in HBM, using space that could otherwise hold model parameters or activations.
  • Software DGE. Descriptors were generated during execution by custom kernels running on the GpSimd Engine, stored in a slice of SBUF. This saved HBM space and kept a compute engine busy calculating addresses.

Hardware DGE generates descriptors as each transfer needs them and leaves GpSimd free for computation. AWS recommends using it wherever possible on Trainium2.

Programming it#

In an NKI kernel, set dge_mode on the transfer instruction.

import nki.isa as nisa

nisa.dma_copy(dst, src, dge_mode=nisa.dge_mode.hwdge)
nisa.dma_transpose(dst=sbuf_dst, src=hbm_src, dge_mode=nisa.dge_mode.hwdge)

Hardware DGE transpose has specific tile shape and data type requirements. NKI dma_transpose reference

The Sync Engine or Scalar Engine issues the command. The compiler can choose the engine, and nisa.dma_copy also accepts an explicit engine argument for hardware DGE. NKI dma_copy reference

Performance notes#

A DGE-based DMA instruction takes about 600 ns on NeuronCore-v3.

When the Scalar Engine issues it, DGE can run alongside earlier Scalar Engine compute such as nisa.activate(). The descriptor hardware and the compute pipeline can work independently.

Limitation#

On NeuronCore-v3, indirect DMA operations such as gather and scatter use software DGE. They take an array of indices to determine which rows to read or write. Trainium2 NKI architecture guide

What is HBM on a Neuron device?HBM

HBM stands for High Bandwidth Memory. On Trainium and Inferentia2, it is the main memory attached to the Neuron device, similar to a GPU's VRAM. It holds model weights, intermediate activations, optimizer state, and the KV cache.

ChipCapacityBandwidth
Inferentia8 GiB (DRAM, not HBM)50 GiB/s
Trainium / Inferentia232 GiB820 GiB/s
Trainium296 GiB2.9 TB/s
Trainium3144 GiB4.9 TB/s in the chip architecture, 4.7 TB/s in the NKI guide

AWS uses "device memory" for both HBM and the DDR memory on first-generation Inferentia. The chip architecture documents list 820 GiB/s for Trainium and Inferentia2, where the NKI architecture guide writes 820 GB/s. Trainium architecture, Trainium/Inferentia2 NKI architecture guide

Where it sits#

On a v2 or later system, data moves through these memories.

LevelMemoryScope
FastestPSUMper NeuronCore, on-chip
SBUFper NeuronCore, on-chip
HBMper device, off-core
SlowestHost DRAMper instance, over PCIe

HBM and host memory store tensors in a linear address space. SBUF and PSUM split data across 128 partitions. A plain DMA copy can distribute tensor rows from HBM across SBUF partitions. A DMA transpose can map a different tensor axis to the partition dimension.

At the model boundary, a typical NKI kernel takes device-memory tensors, loads tiles into SBUF, computes on them and stores the result back to HBM. The host framework moves tensors between host and device memory.

How bandwidth affects token generation#

In a batch-one decode step for a dense language model, each large weight matrix is typically read from HBM and used once. That is little work per byte moved, so decoding is often memory-bound.

A weight-only ceiling for token throughput is:

tokens/sec ≈ HBM bandwidth / bytes of model weights

A 70B model has about 140 GB of BF16 weights and needs more than one 96 GiB Trainium2 chip. If two chips stream a balanced share of the weights at their combined peak of 5.8 TB/s, the idealized bandwidth ceiling is about 41 tokens/s at batch one. That estimate excludes KV-cache traffic and inter-chip communication. FP8 approximately halves the bytes needed for the weights.

Note that the bandwidth figures above are per chip, shared across all of its NeuronCores — 2.9 TB/s serves eight cores on Trainium2.

Pooling#

NeuronLink makes the HBM of multiple chips directly addressable from any chip in the pool: up to 16 chips on Trn1, 64 on a Trn2 UltraServer and 64 or 144 on a Trn3 UltraServer. The memory is still physically distributed, so remote and local accesses use different paths.

Data movement between HBM and SBUF is done by DMA engines, which run in parallel with computation and support inline compression and decompression.

What is a DMA engine?

Direct memory access (DMA) engines move data independently of the hardware that performs computations. On a Neuron device they carry tensors between HBM and SBUF, between SBUF and SBUF, and between chips.

These counts and peak DMA bandwidths are per chip.

ChipDMA enginesDMA bandwidth
Trainium / Inferentia2321 TB/s
Trainium21283.5 TB/s
Trainium31284.9 TB/s

Trainium3 NKI architecture guide, Trainium3 chip architecture

On Trainium2, each NeuronCore-v3 is typically uses 16 DMA engines in parallel to make use of its SBUF bandwidth.

DMA transfers run in parallel with computation. This is the mechanism behind latency hiding: while the Tensor Engine works on tile n, DMA engines can fetch tile n+1. If the next tile arrives in time, computation can continue without waiting for the load.

A sequencer starts a transfer with a control instruction. The Sync Engine can issue that instruction on a separate stream from the compute engines.

Inline compression#

Neuron DMA engines perform inline memory compression and decompression as data moves, from Trainium and Inferentia2 onward. The benefit depends on how well the data compresses. Trainium3 also introduces operations such as adding incoming values to an existing SBUF tensor during a transfer.

DMA transpose#

From Trainium2, DMA engines can swap tensor axes during a transfer from HBM to SBUF or between SBUF tensors. This lets a transfer place the axis the Tensor Engine needs across the partitions in SBUF.

For example, attention may store keys as [seqlen, d_head] in the KV cache. When the Tensor Engine computes attention scores, it sums over d_head. A DMA transpose puts that axis in the SBUF partition dimension during the load.

For Trainium2, AWS reports up to 90% DMA throughput utilization for an HBM-to-SBUF transpose with suitable access patterns, up to 100% for a plain copy, and up to 50% for an SBUF-to-SBUF transpose. Trainium2 NKI architecture guide

Descriptors#

A DMA transfer uses descriptors that give the source and destination addresses, sizes and strides. Neuron can generate them in several ways.

  • Static. Descriptors generated on the host when the NEFF is loaded, and stored in HBM.
  • Software DGE. Generated at runtime by custom kernels on the GpSimd Engine, using SBUF for storage.
  • Hardware DGE. From NeuronCore-v3, a dedicated Descriptor Generation Engine generates them on demand without using the GpSimd Engine or reserving descriptor space in HBM or SBUF.

Ordering#

Trainium used write-after-write DMA barriers. Trainium2 uses strong-order-write, which is generally faster, by an amount that depends on transfer size.

Separately, each of the eight processors in a NeuronCore-v3 GpSimd Engine has its own integrated DMA engine — 307 GB/s across all eight — running in parallel with both GpSimd compute and the main DMA engines.

What is EFA?EFA

EFA, the Elastic Fabric Adapter, is AWS's high-performance EC2 network interface. On supported Neuron instances it carries collective communication across NeuronLink domains, including between standalone instances or between UltraServers. With EFA's OS bypass, a userspace application can send and receive data through the Libfabric networking library without going through the operating system's network stack. AWS EC2 EFA documentation

For the one-chip trn2.3xlarge, EC2 lists EFA support and 200 Gbps of network bandwidth. The Trn2 architecture entry explains where the Neuron guide differs.

Bandwidth in perspective#

On a standalone Trn2 48xlarge, 3,200 Gbps is 400 GB/s for the instance. If all 16 chips split the bandwidth evenly, that would be 25 GB/s per chip. Within the instance, NeuronLink-v3 is rated at 1,024 GiB/s per chip. The figures describe different paths and scopes, but illustrate why frequent tensor-parallel collectives often stay on NeuronLink. The rate you measure depends on the collective and where its participants run.

EFA is the scale-out fabric of an UltraCluster. To measure collective bandwidth, use nccom-test.

What is the GpSimd Engine?

The GpSimd Engine (GpSimdE) is a group of eight programmable 512-bit vector processors in each NeuronCore starting with v2. They can run C/C++ programs and read and write SBUF directly.

Where the Tensor, Vector, and Scalar engines are specialized for particular operations, GpSimd can run general-purpose code. For example, a kernel can use it to apply a triangle-shaped mask to a tensor without sending the tensor back to the host CPU.

Custom operators#

The legacy Neuron Custom C++ Operators library exposes GpSimd for custom operators on NeuronCore-v2. AWS directs developers writing new operators to NKI, which can use the specialized engines directly.

Generation notes#

On NeuronCore-v3, each of the eight processors gains its own integrated DMA engine. These run in parallel with GpSimd computation and in parallel with the device's main DMA engines, and they can reach SBUF or HBM on chips in the same Trn2 instance. All eight together provide 307 GB/s, split as 153 GB/s per direction.

Also on v3, the Vector and GpSimd engines can access SBUF in parallel, which was disallowed on v2. The two share a memory bus that the Vector Engine's performance mode also uses, with the hardware arbitrating between them.

GpSimd can also generate DMA descriptors at runtime. On v3 and later, the dedicated Descriptor Generation Engine can handle supported transfers and leave GpSimd available for other work.

NeuronCore-v4 keeps the same eight-processor structure and programmable C/C++ hardware. The legacy aws-neuronx-gpsimd-customop-lib package is documented for v2 (Trn1 and Inf2) and entered maintenance in Neuron 2.33.0. The v4 architecture guide describes the programmable hardware. NeuronCore-v4 architecture, Custom C++ library release notes, Maintenance announcement

In AWS's abbreviations this appears as GpSimdE.

Inf1 is the EC2 instance family powered by first-generation Inferentia chips. AWS launched it in 2019 for model inference.

Each chip carries four NeuronCore-v1 cores, so a full inf1.24xlarge exposes 64 NeuronCores.

Inf1 supports NeuronCore Pipeline over NeuronLink-v1: a model is split by layer across several cores. The cores pass intermediate results along the chain and can keep their own weights in on-chip memory when those weights fit.

Model fit#

AWS's Inf1 examples include convolutional networks such as ResNet-50 and encoders such as BERT-base. For large language models, each chip's 8 GiB limits how many weights it can hold, and 50 GiB/s limits how fast it can read them during memory-bound decoding.

The 128 GiB on inf1.24xlarge is the sum of 16 separate 8 GiB memories. Directly addressable memory pooling arrived with NeuronLink-v2.

Software#

Inf1 uses the legacy neuron-cc compiler and archived framework integrations, including torch-neuron for older PyTorch and tensorflow-neuron for TensorFlow. Modern TorchNeuron, PyTorch NeuronX and NKI target newer hardware. Moving an Inf1 model to a newer accelerator requires compiling for the new target with its supported framework. /device-hardware/neuroncore

What is a NeuronCore?NC

A NeuronCore is the independent compute unit inside a Neuron device. It is the closest thing Neuron has to an NVIDIA Streaming Multiprocessor in the sense that both are compute units within a larger chip.

A NeuronCore combines several engines that specialize in different operations and share on-chip memory.

  • The Tensor Engine multiplies matrices on a systolic array.
  • The Vector Engine handles operations such as sums and normalization that combine multiple values.
  • The Scalar Engine handles element-wise operations such as applying an activation to each input value.
  • The GpSimd Engine contains programmable C/C++ processors for operations that do not map well to the specialized engines. It first appeared in v2.
  • The Sync Engine can schedule DMA transfers independently of the compute engines on v2 and later.

The main working memory on the core is SBUF. The Tensor Engine reads its inputs from SBUF and writes its results to PSUM, a smaller buffer where it can add successive partial results.

How engines work together#

Each engine has its own sequencer, the hardware that fetches, decodes and issues instructions. That lets the engines run different operations at the same time. In an NKI kernel, you choose which engines act on each tile, or block of data.

When one engine needs another engine's result, hardware semaphores enforce the ordering. The Neuron compiler works out those dependencies and inserts the semaphore operations, including for hand-written NKI kernels.

For example, the Tensor Engine can multiply one pair of tiles while the Vector Engine moves a finished result out of PSUM and the DMA engines load the next tile. See engine parallelism.

What v3 introduced#

Double-rate FP8 matmul. Each element of the 128×128 array can perform two FP8_E4 or FP8_E5 multiply-accumulates per cycle. A packed FP8 instruction can therefore cover 256 values along the contraction dimension, the axis the matmul sums over. The sum stays in FP32. FP8_E3 runs at the BF16 rate.

/device-hardware/psum

What is PSUM?PSUM

PSUM, the Partial Sum Buffer, is a small on-chip memory in a NeuronCore, dedicated to holding Tensor Engine matrix multiplication results and partial sums.

It is 2 MiB on NeuronCore-v2, v3 and NeuronCore-v4. It has 128 partitions of 16 KiB each. Each partition has eight 2 KiB banks. Trainium3 NKI architecture guide

How it accumulates partial results#

In a standard, unpacked matrix multiplication, the Tensor Engine can handle up to 128 values along the contraction dimension K, the axis it sums over. For K = 4096, computing one output tile takes 32 nc_matmul calls whose results add up to the final tile.

The Tensor Engine can add each partial result to the running total in PSUM. That is near-memory accumulation. It saves a separate reduction pass and avoids copying the partial results through SBUF.

PSUM banks and matmul tile width#

On NeuronCore-v3, one nc_matmul output fits in one bank per partition, which holds 512 FP32 elements. On NeuronCore-v4, one output can span all eight banks for up to 4,096 FP32 or 8,192 BF16 elements per partition. A wide output can leave fewer banks available for other tiles. NKI nc_matmul reference

Getting data back out#

The Tensor Engine writes all matmul results to PSUM. The Vector or Scalar Engine typically copies a finished result to SBUF so the next matmul can reuse the space.

On NeuronCore-v3, the Vector and Scalar engines can access PSUM in parallel at full bandwidth, as long as they do not target the same bank — a restriction on v2, where those accesses had to serialize.

Orientation#

Input streams into the systolic array along one axis and results come out along the other. In stationary.T @ moving, the free dimension of stationary becomes the partition dimension of the PSUM output.

Floating-point matmul accumulates in FP32 inside the Tensor Engine. On v4 it can write a BF16 destination in PSUM. When adding to a BF16 partial sum, it upcasts the stored value, adds in FP32 and rounds back to BF16 on each write. The v3 transpose mode also supports FP16/BF16 destinations. What is SBUF?SBUF

SBUF, the State Buffer, is the main on-chip working memory in a NeuronCore. The compiler or kernel loads data into SBUF from device memory so the compute engines can use it. Like GPU shared memory, the program controls what goes into it and when.

Partitions and capacity#

SBUF has 128 partitions, each a region of memory. The partitions line up with the 128 rows of the systolic array in the Tensor Engine.

CoreTotal SBUFPer partition

Per chip that is 48 MiB on Trainium, 224 MiB on Trainium2, and 256 MiB on Trainium3.

Access rules#

  • The Vector, Scalar and GpSimd engines can read and write SBUF.
  • The Tensor Engine reads its inputs only from SBUF, and writes its outputs only to PSUM.
  • Data moves between SBUF and HBM by DMA only.
  • Data moves between SBUF and PSUM by compute-engine instructions, not DMA.

Reusing data in SBUF reduces the bytes read from HBM and raises arithmetic intensity.

Who moves data#

An NKI kernel or the Neuron compiler schedules transfers into and out of SBUF. Keeping data there for reuse depends on the schedule and available capacity. See software-managed memory.

If the live data in a kernel exceeds SBUF capacity, the compiler inserts spills and refills to HBM. This is called spilling and adds HBM traffic. Tiling helps keep the working set small enough to fit.

Layouts#

On Trainium, SBUF was row-major only. Trainium2 added Col-major-2B and Col-major-4B layouts, which removes some transposes that previously had to be done explicitly.

NeuronCore-v4 adds near-memory accumulation: DMA engines can do a read-add-write into existing SBUF contents in a single transfer. AWS documents the hardware feature without an nki.isa API in Neuron 2.33.1. Trainium3 NKI architecture guide

/device-hardware/sync-engine

What is the Sync Engine?

The Sync Engine (SyncE, sometimes SP) is a control unit in NeuronCore-v2 and later. It can start DMA transfers and synchronize operations independently of the compute engines.

A compute engine's sequencer directs its own stream of instructions. It can issue two kinds of instruction.

  • Control instructions run on the sequencer itself. They can branch, compute an address in private 32-bit registers, or start a DMA transfer.
  • Data path instructions perform tensor operations using SBUF and PSUM.

The Sync Engine is a separate sequencer that runs control instructions. It can start loading the next tile while the Tensor Engine works on the current one. See latency hiding.

Synchronization#

The compute engines run asynchronously and in parallel, so data dependencies between them need enforcement. That is done with atomic hardware semaphores.

The Neuron compiler analyzes the data dependencies in your graph or NKI kernel and inserts the semaphore operations so a consumer waits until its input is ready.

On NeuronCore-v3, the Sync Engine is one of the two sequencers that can drive the Descriptor Generation Engine; the Scalar Engine is the other. The compiler can choose a sequencer, and nisa.dma_copy also allows the caller to select it.

The Sync Engine appears in AWS's glossary as "the SP engine".

/device-hardware/systolic-array

What is a systolic array?

A systolic array is a grid of simple processing elements, each doing a multiply-accumulate, which multiplies two numbers and adds the product to a running sum. The elements pass data to their neighbors, reusing it as it moves through the grid. The Tensor Engine uses a 128 × 128 array in the NeuronCore generations covered by NKI.

How the array reuses data#

In a systolic array, each input element is read from SBUF once, then reused across an entire row or column of processing elements. With a full row or column, one read can feed up to 128 multiply-accumulates.

Why 128 is everywhere#

The shape of the array determines how standard matmul instructions lay out their inputs.

  • SBUF and PSUM have 128 partitions, one per row of processing elements.
  • An on-chip tile can use up to 128 partitions.
  • The contraction dimension of a matmul must map to the partition dimension, because that is the axis the array accumulates along.
  • The stationary matrix's free axis is capped at 128, the number of columns.

See tiling for how NKI breaks larger matrices into blocks that fit these limits.

The tradeoffs#

Tile shape and data layout affect how much of the array is useful.

  • Small matrices use less of the array. A narrow tile can leave rows or columns idle. The cost also depends on which input is stationary and whether hardware tiling mode is enabled.
  • Sparsity does not help unless it is structured in a pattern the hardware recognizes — hence the 4:16 through 1:2 patterns on v3 and later.
  • There is a pipeline fill and drain cost. Data has to propagate across the grid before the first result emerges. For a long stream of matmuls, the rate depends on how often the engine can accept a new instruction.

The 128×128 shape is also why FP8 doubling works the way it does on NeuronCore-v3: the grid stays 128×128 physically, but each processing element performs two FP8 multiply-accumulates per cycle, which the programmer sees as a 256×128 array.

←Sync Engine→Tensor Engine
/device-hardware/tensor-engine

What is the Tensor Engine?

The Tensor Engine (TensorE) is the matrix multiplication unit in a NeuronCore. Its peak rate depends on the input format. On NeuronCore-v3, for example, it can reach 79 TFLOPS for BF16 matrix multiplication if data arrives fast enough to keep the array busy.

It uses a systolic array, a grid of 128 × 128 processing elements on NeuronCore-v2 through v4. It handles general matrix multiplication (GEMM), convolution, and transpose. It plays a role similar to NVIDIA's Tensor Cores.

Where inputs and outputs go#

The Tensor Engine reads only from SBUF and writes only to PSUM. A typical matmul kernel loads a tile from HBM into SBUF, computes into PSUM, then uses the Vector or Scalar engine to copy the finished result back to SBUF and make room for the next output.

Floating-point matmul accumulates in FP32 inside the Tensor Engine. The ordinary matmul destination is FP32 on NeuronCore-v3. NeuronCore-v4 also supports a BF16 destination, rounding on each write to PSUM. The v3 transpose mode supports 16-bit destinations. Trainium3 NKI architecture guide

Stationary and moving#

One NKI matmul call typically appears as two hardware instructions.

  1. LoadStationary loads one matrix from SBUF and caches it inside the array.
  2. MultiplyMoving streams the second matrix across it, producing output into PSUM.

So nki.isa.nc_matmul(dst, stationary, moving) computes stationary.T @ moving. The free axis of stationary becomes the output's partition axis, while the free axis of moving becomes the output's free axis. Choosing the order that the next operation expects can save a transpose. See stationary and moving.

Using it for data movement#

Because the array multiplies by whatever you load, you can construct matrices of zeros and ones to rearrange or combine data.

  • Transpose. On v2, multiplying by an identity matrix transposes the input but can propagate NaN or Inf to other positions. Starting with v3, Tensor Engine transpose preserves the input bits.
  • Broadcast. Multiplying by a vector of ones repeats values across partitions.
  • Cross-partition sum. A single column of the array can sum values along the partition axis.

These operations occupy the Tensor Engine. A DMA transpose can move data and transpose it at the same time, leaving the Tensor Engine available for matrix multiplication. NKI nc_transpose reference

What is Trainium?

Trainium, also called Trainium1, is AWS's first purpose-built chip for model training. It is the second Neuron hardware generation and powers the Trn1 and Trn1n instances.

Each Trainium chip has the following hardware.

  • Two NeuronCore-v2 cores, together delivering 380 INT8 TOPS, 190 FP16/BF16/cFP8/TF32 TFLOPS, and 47.5 FP32 TFLOPS.
  • 32 GiB of HBM at 820 GiB/s.
  • 1 TB/s of DMA bandwidth, with inline memory compression and decompression.
  • NeuronLink-v2, four links per chip, for collectives and memory pooling across chips.

Trainium and Inferentia2 both use NeuronCore-v2. A full Trn1 instance has 16 chips, four NeuronLink-v2 links per chip, and EFA for scaling across instances.

What made it a training chip#

Three additions in NeuronCore-v2 help with training.

  • Stochastic rounding. Round-to-nearest can repeatedly lose small updates to BF16 weights. Stochastic rounding chooses between nearby representable values so the update is preserved on average. This can enable BF16 training without keeping a separate FP32 copy of the weights.
  • Control flow and dynamic shapes, so a training loop's data-dependent branches stay on device.
  • The GpSimd Engine, so a novel loss or optimizer can be written as a custom operator rather than falling back to the host.

On a 16-chip Trn1 instance, NeuronLink-v2 lets any chip directly address another chip's HBM. EFA lets Trn1 instances communicate across an UltraCluster, which AWS describes as designed to scale to over 100,000 chips.

Software and newer chips#

Trainium2 has three times the HBM capacity and about 3.5× the BF16 throughput per chip. Current TorchNeuron and vLLM Neuron target Trainium2 and Trainium3. See Trn1 for the older serving path. AWS Trainium architecture, AWS Trn1 architecture

What is the Vector Engine?

The Vector Engine (VectorE) handles operations that combine values, such as summing a row for softmax or adding two tensors element by element.

Reductions in normalization and softmax do little arithmetic per byte moved. They can limit a kernel's throughput even when the Tensor Engine has capacity to spare. See arithmetic intensity.

It can read and write both SBUF and PSUM. After the Tensor Engine writes a matrix multiplication result to PSUM, the Vector Engine can move it to SBUF and make room for the next result.

Performance mode#

On NeuronCore-v3 the Vector Engine has a BF16/FP16 performance mode that gives up to 4× the v2 instruction throughput for selected instructions. The engine still does the arithmetic in FP32.

The hardware selects the mode automatically based on the instruction, where its inputs and outputs live, their types and their layout.

  • 4× for tensor_copy and tensor_scalar when both input and output are in SBUF, both are BF16 or FP16, and the innermost free dimension is physically contiguous.
  • 2× for tensor_copy and tensor_scalar when either side is in PSUM with the same type and layout conditions, or when both are in SBUF and BF16/FP16 with a noncontiguous innermost free dimension.
  • 2× for tensor_tensor when both inputs are in SBUF and everything is BF16/FP16.

This mode uses a memory bus shared by the Vector and GpSimd engines, with the hardware deciding which engine can use it.

On NeuronCore-v4 the Vector Engine gains two more capabilities: quantizing BF16/FP16 down to MXFP8, useful between MLP layers, and a fast exponential at 4× the throughput of exp on the Scalar Engine for operations such as attention softmax. Trainium2 NKI architecture guide

How the doubling works#

What are collectives on Neuron?

Collective operations move or combine data across a group of workers, each identified by its rank. Neuron runs them on dedicated CC-Cores, which allows communication to overlap with compute when dependencies and scheduling permit. AWS compute-communication overlap guide

OperationWhat it does
All-reduceCombine corresponding values, for example by summing, and return the result to every rank
All-gatherConcatenate all ranks' data and return the result to every rank
Reduce-scatterReduce values across ranks and give each rank a slice
All-to-allRedistribute one piece from each source rank to each destination rank
Collective-permuteSend each rank's data to a specified destination rank

Tensor parallelism often reduces partial activations across shards. Data parallelism synchronizes gradients. Mixture-of-experts routing can use all-to-all.

Where they run#

NeuronLink carries traffic within a connected set of chips. The 16 chips of a trn2.48xlarge form a 4×4 grid with links that wrap around its edges. A Trn2 UltraServer adds NeuronLink rings connecting matching positions across four hosts. EFA carries traffic between NeuronLink domains. The cost depends on the SKU, rank placement, message size and collective algorithm. Use nccom-test to measure the paths and group sizes your workload uses. Issuing collectives#

Frameworks and libraries such as TorchTitan Neuron and vLLM Neuron use collectives to implement sharding. The Neuron Runtime executes them on hardware.

Hand-written NKI kernels can use nki.collectives directly. A ReplicaGroup identifies which ranks act together. This fragment sums one tensor per rank and writes the same sum to every rank. Inside the kernel, world_size is the total number of ranks, supplied as a Python integer at specialization. Allocate matching tensors src and dst in private HBM before calling it.

import nki.collectives as ncc
import nki.language as nl

replica_group = ncc.ReplicaGroup.from_partition_op(
    world_size, ncc.rg_partition_op.bitwise_and, 0
)
ncc.all_reduce(srcs=[src], dsts=[dst], replica_group=replica_group, op=nl.add)

The source and destination are lists so one call can reduce several HBM tensors together. The allowed buffers and layouts vary by operation and LNC setting. AWS all-reduce API · AWS ReplicaGroup API

/device-software/dma-transpose

What is DMA transpose?

DMA transpose swaps tensor axes during a transfer to SBUF. The DMA engines can read from HBM or from SBUF without occupying a compute engine. On Trainium2, AWS documents bit-accurate transposes for 2-byte and 4-byte types. Trainium2 NKI architecture guide

import nki.language as nl
import nki.isa as nisa

# hbm_src: [512, 128]
sbuf_dst = nl.ndarray((128, 512), dtype=hbm_src.dtype, buffer=nl.sbuf)
nisa.dma_transpose(dst=sbuf_dst, src=hbm_src)

Why it is needed#

In a packed, row-major HBM matrix, each row is a contiguous run of values. A straight copy to SBUF puts each row into its own partition. A DMA transpose puts each source column into its own partition instead.

For example, an attention kernel can store a key cache in HBM as [seqlen, d_head]. The matmul Q @ K.T sums over d_head, so NKI needs that axis in the partition dimension. The transpose puts the cache tile into SBUF as [d_head, seqlen].

Trainium2 throughput#

OperationShare of peak DMA throughput
Plain DMA copyup to 100%
HBM→SBUF transposeup to 90%
SBUF→SBUF transposeup to 50%

Reaching these rates requires suitable access patterns. On Trainium2 each NeuronCore-v3 is paired with 16 DMA engines. The fastest transpose access pattern lets all 16 work together, writing a block of [128, 16] at a time. Use all 128 output partitions and make the innermost free dimension a contiguous multiple of 16 to approach the peak. Smaller tiles and other valid shapes can run at lower throughput.

Versus Tensor Engine transpose#

The alternative is transposing on the Tensor Engine, either by multiplying against an identity matrix or, from NeuronCore-v3, with a real transpose mode.

On Trainium2, a Tensor Engine transpose can be faster by itself. If the next operation needs the result in SBUF, the Vector or Scalar engine must copy it there from PSUM. DMA transpose can save that copy in kernels where those engines are already busy, for example with attention softmax.

Before NeuronCore-v3, Tensor Engine transposes had a correctness hazard as well: multiplying by an identity propagates NaN/Inf through the accumulation chain, so the result is not a bit-accurate transpose. v3's explicit transpose mode fixed that.

←Data types→Free dimension
/device-software/free-dimension

What is the free dimension?

The free dimensions of a tile are the axes after the first. The partition dimension maps the first axis across physical partitions. The free dimensions describe the elements within each partition.

tile = nl.ndarray((128, 512), dtype=nl.bfloat16, buffer=nl.sbuf)
#                       ^^^ free dimension

The free dimensions can be wider than 128. A tile of shape (128, 4, 512) has two free axes and puts 4 × 512 elements in each partition.

Capacity and matmul limits#

  • Partition capacity. 192 KiB per SBUF partition on NeuronCore-v2, 224 KiB on v3, and 256 KiB on v4. All free dimensions together must fit.
  • The moving free axis of a matmul is at most 512 elements on v2 and v3, fitting one PSUM bank for FP32 output. On v4 it can use eight banks for up to 4,096 elements with FP32 output or 8,192 with BF16. NKI nc_matmul reference, Trainium and Inferentia2 NKI architecture guide
  • The stationary free axis can hold 128 elements, one for each of the systolic array columns.

Why the ordering matters#

The innermost free axis is the fastest-varying one in a packed tile. On Trainium2, Vector Engine tensor_copy and tensor_scalar on BF16 or FP16 SBUF tiles can run at 4× v2 throughput when that axis is contiguous in both operands. With the same types and buffers but a strided axis, the documented gain is 2×. Contiguous runs also give the DMA engines larger chunks to transfer. Trainium2 NKI architecture guide

In matmul output#

The free axis of the moving tensor becomes the free axis of the output, while the free axis of the stationary tensor becomes the output's partition axis. You can choose the roles to put the output in the layout the next operation expects.

/device-software/mxfp8

What are MXFP8 and MXFP4?

MXFP8 and MXFP4 are Open Compute Project floating-point formats that store a scale for each small group of values. This is called microscaling. Each group can represent a different range of magnitudes, which helps when one part of a tensor has much larger values than another. MXFP4 uses four data bits per value and MXFP8 uses eight, plus the scale shared by the group.

On Trainium3#

The NeuronCore-v4 Tensor Engine reads one 8-bit scale per 32 elements along the axis the matmul sums over. It can multiply an MXFP8 matrix by an MXFP4 matrix and apply their scales in the same instruction. It converts MXFP4 data to MXFP8 before doing the math. Trainium3 peaks at 2,517 TFLOPS per chip for either format, about four times its BF16 rate. AWS Trainium3 chip specifications, Trainium3 NKI architecture guide, NeuronCore-v4 architecture

In NKI#

nki.isa.nc_matmul_mx reads the stationary and moving tiles from SBUF, along with one scale tensor for each. Each packed element contains four values along the contraction axis. At 128 partitions, one matmul therefore covers 512 contraction elements. The Tensor Engine accumulates in FP32. The PSUM destination can be FP32 with a moving free dimension of up to 4,096, or BF16 with up to 8,192. Both limits use all eight PSUM banks. NKI nc_matmul_mx reference

The v4 Vector Engine can use nki.isa.quantize_mx to produce MXFP8 data and scales from BF16 or FP16 in SBUF. This lets a kernel quantize intermediate activations before the next matmul without moving them through HBM. Ordinary FP8 inputs are available through nki.isa.nc_matmul. What is a NEFF?NEFF

A NEFF is a file in the Neuron Executable File Format. It holds code that runs on a Neuron device. The Neuron Compiler produces it. The Neuron Runtime loads it into device memory and executes it. It is analogous to a CUDA cubin.

A NEFF holds engine instructions and the compiled plan for moving data through SBUF, PSUM and device memory. Weights can be embedded or supplied separately, depending on the framework export. AWS NEFF generation guide

When compilation happens#

The framework chooses when to produce the NEFF and how much work to put in it.

  • TorchNeuron can compile a single operator in eager mode or a captured graph on first use with torch.compile.
  • A serving stack such as vLLM Neuron can compile graphs for shape buckets during warmup or ahead of deployment.
  • Legacy torch_neuronx.trace produces a TorchScript artifact that embeds the NEFF and can be saved for later inference.

The compiled code targets specific hardware and input shapes and types. A different shape or option can require another compilation. A matching compilation cache entry can supply the executable without running the compiler again. Compiling a larger graph lets the compiler plan tiling, data movement and synchronization across operators. See software-managed memory for what that plan controls.

What is NKI?NKI

NKI, the Neuron Kernel Interface, is a Python API and compiler for writing kernels that run on the engines inside a NeuronCore. A kernel can implement a single operation or combine several operations so they can reuse data in on-chip memory.

This NKI 0.7 kernel adds two tensors with the same shape and data type. It loads each input as a single tile, so the first axis can have at most 128 entries and the inputs and result must fit in SBUF. Run it with LNC=1.

import nki
import nki.language as nl

@nki.jit
def add_kernel(a_tensor, b_tensor):
    out = nl.ndarray(a_tensor.shape, dtype=a_tensor.dtype, buffer=nl.shared_hbm)
    a = nl.load(a_tensor)
    b = nl.load(b_tensor)
    nl.store(out, value=nl.add(a, b))
    return out

The inputs and output live in HBM. nl.load brings each input into SBUF before the add. The result goes back to HBM through nl.store. These transfers are explicit because Neuron memory is software-managed.

How a kernel runs#

  • nki.language provides buffers, data types, loops and high-level operations. A convenience operation can lower to one or more hardware instructions.
  • nki.isa exposes low-level operations and their operands. Use it when tuning engine use, memory layout or instruction scheduling.

@nki.jit marks the kernel entry point. In NKI 0.7, Python runs at compile time to decide which operations to emit. A branch on input shape, for example, emits only the operations for the shape seen at compilation. The compiler turns those operations into device instructions on tiles and tells engines when to wait for one another's results. Use the nki.* modules for current kernels. The previous neuronxcc.nki.* namespace has a different API. AWS NKI language guide · AWS NKI migration guide

Using kernels in models#

Native TorchNeuron can call a @nki.jit kernel directly on Neuron tensors in eager mode or inside torch.compile(backend="neuron"). For a named PyTorch custom operator, decorate a typed wrapper with torch_neuronx.nki_op and declare any mutated arguments in mutates_args. To train through the operator, register its backward function with .register_autograd. JAX integration is also available. AWS guide to NKI in TorchNeuron · AWS framework integration guide

The NKI Library offers tuned kernels for common operations. The NKI CPU simulator runs kernels locally for debugging and correctness checks.

/device-software/nki-language

What is nki.language?

nki.language, conventionally imported as nl, is the high-level API for NKI. Use it to create tensors in specific memories and express operations and loops. The compiler turns its NumPy-style operations into nki.isa instructions. AWS marks convenience operations such as nl.load, nl.store and nl.softmax as experimental. AWS nki.language API

This kernel computes softmax across the columns of each row. Run it with LNC=1. Each batch of rows keeps the full width in SBUF. Leave room for the softmax intermediates.

import nki
import nki.language as nl

@nki.jit
def softmax_kernel(in_tensor):
    out = nl.ndarray(in_tensor.shape, dtype=in_tensor.dtype, buffer=nl.shared_hbm)
    rows = in_tensor.shape[0]
    tile_rows = nl.tile_size.pmax
    for start in range(0, rows, tile_rows):
        stop = min(start + tile_rows, rows)
        tile = nl.load(in_tensor[start:stop, :])
        nl.store(out[start:stop, :], value=nl.softmax(tile, axis=1))
    return out

Neuron memory is software-managed. A tensor's buffer determines which instructions can access it.

Specialization and device loops#

The NKI 0.7 frontend unrolls Python for and while loops whose bounds or conditions it can evaluate at compile time. It traces the body once for each iteration. ←NKI Library→Partition dimension
/device-software/partition-dimension

What is the partition dimension?

The partition dimension is the first axis of any tile in SBUF or PSUM. These memories have 128 physical partitions, so the first axis can hold at most 128 entries. In a 2-D tile, each row occupies one partition.

tile = nl.ndarray((128, 512), dtype=nl.bfloat16, buffer=nl.sbuf)
#                  ^^^ partition dimension, maximum 128
#                       ^^^ free dimension

Why 128#

For matrix multiplication, each of the 128 SBUF partitions feeds one row of processing elements in the systolic array. The limit comes from that physical layout.

Which axis goes first in a matmul#

In an ordinary, unpacked matmul, put the contraction dimension on the partition axis of both inputs.

The contraction dimension is the axis you sum over, K in A[M, K] @ B[K, N]. To compute this with nc_matmul, pass A in [K, M] layout and B in [K, N] layout. Double-rate FP8 and MX matmul pack more than one contraction element into each partition. NKI nc_matmul reference

For example, an attention kernel can store keys in HBM as [seqlen, d_head]. Computing Q @ K.T contracts over d_head. A DMA transpose can move the keys to SBUF as [d_head, seqlen] in the same transfer.

Working with it#

In current NKI, the first axis of the shape passed to nl.ndarray is the partition axis for SBUF and PSUM. For a leading axis of 300 elements, tile it into 128, 128, and 44 elements. A loop over range(0, 300, 128) covers all three, including the final partial tile. AWS data representation guide

On NeuronCore-v3, an SBUF partition holds 224 KiB and a PSUM partition holds 16 KiB. Move completed matmul results out of PSUM to make room for the next output tiles.

←nki.language→Rounding mode
/device-software/rounding-mode

What are Neuron rounding modes?

The rounding mode determines which value Neuron stores when a floating-point result falls between two representable values.

  • RNE (round nearest, ties to even) selects the nearest representable value. At an exact tie, it picks the value with a zero in the last significand bit. This is the default.
  • SR (stochastic rounding) chooses either neighboring representable value, with probability proportional to the proximity of the exact result.

RNE is available on all NeuronCore generations. Stochastic rounding is available starting with NeuronCore-v2. AWS rounding modes

Small updates in low precision#

Suppose an update adds 0.5 to an FP16 value of 1024.0. The exact result is halfway between 1024.0 and 1025.0. RNE chooses 1024.0 every time, so repeatedly adding the increment to the rounded result leaves it unchanged. Stochastic rounding picks 1025.0 half the time, preserving the increment in expectation.

The same problem arises when a training update is small relative to a BF16 weight. Stochastic rounding can help such updates accumulate and can make a full-precision master copy of weights unnecessary for some workloads. That saves HBM, with convergence depending on the training recipe. AWS rounding modes and accumulation example

Runtime settings#

Set NEURON_RT_STOCHASTIC_ROUNDING_EN=1 to enable stochastic rounding in the runtime. For controlled comparisons, the Neuron Runtime also exposes NEURON_RT_STOCHASTIC_ROUNDING_SEED. AWS runtime environment variables

/device-software/software-managed-memory

What is software-managed memory?

Memory on a NeuronCore is software-managed. The kernel or Neuron Compiler schedules the transfers between device memories. AWS memory hierarchy guide

A CPU or GPU cache can fetch a missing line automatically. NeuronCore has no such cache between device memories. To compute on data in HBM, the program issues a DMA transfer to SBUF.

Consequences#

  • Estimate arithmetic intensity by counting the operations and bytes transferred in the schedule. The compiler can insert extra transfers for spills, so check a profile when the numbers disagree.
  • Work in tiles to fit the available on-chip memory. Keep a tile in SBUF for reuse when possible. Issuing another load moves those bytes from HBM again.
  • Schedule a DMA transfer for the next tile while the Tensor Engine uses the current one. See latency hiding.

neuronx-cc encodes the memory plan in a NEFF. In TorchNeuron eager mode, the backend compiles or reuses device code for each supported operator as PyTorch calls it.

←Rounding mode→Stationary & moving
/device-software/stationary-and-moving

What are stationary and moving matrices?

A matrix multiplication on the Tensor Engine has two inputs. The stationary matrix stays in the systolic array while the moving matrix streams through it.

  • LoadStationary (LS) loads the stationary matrix into the array.
  • The moving matrix is streamed by a MultiplyMoving (MM) instruction, multiplying against the held stationary matrix and writing results to PSUM.

One nki.isa.nc_matmul call lowers to those two hardware instructions.

# stationary: [K, M], moving: [K, N], dst: [M, N]
nki.isa.nc_matmul(dst, stationary, moving)  # stationary.T @ moving

In this unpacked matmul, both inputs put the contraction dimension K on the partition axis. That is why the math reads stationary.T @ moving.

The layout rule#

The free axis of stationary becomes the partition axis of the output. The free axis of moving becomes the free axis of the output.

The layout follows the geometry of the array. Results emerge along the axis perpendicular to the input partitions, so AWS's architecture diagrams draw the PSUM partition dimension at a right angle to SBUF's. Trainium2 NKI architecture guide

Choosing the output layout#

You can swap the roles, and you get a transposed result:

nki.isa.nc_matmul(dst_mn, x, y)  # [M, N]
nki.isa.nc_matmul(dst_nm, y, x)  # [N, M]

If both inputs fit the chosen roles, choose the order that gives the next operation the layout it needs. For example, if it needs N on the partition axis, produce [N, M] directly and save a transpose.

Tile size limits differ by role#

The two roles have different caps, which is another reason the assignment matters. For a standard nc_matmul with hardware tiling mode off:

Double-rate FP8#

On NeuronCore-v3, the double-rate FP8 mode extends the contraction dimension to 256 by giving each processing element two multiply-accumulates per cycle. Both operands take an extra axis of size exactly 2:

# stationary: [128, 2, 128]   moving: [128, 2, 512]   dst: [128, 512]
nisa.nc_matmul(dst, stationary, moving, perf_mode=nisa.matmul_perf_mode.double_row)

LoadStationary places two values in each processing element. MultiplyMoving streams in two matching values so the element can compute both products in the same cycle. Zero-pad an odd contraction length before packing it into the two axes.

/device-software/structured-sparsity

What is structured sparsity?

Structured sparsity is a regular pattern of zeros in a matrix. On NeuronCore-v3 and v4, the Tensor Engine can use that pattern to skip multiplications by zero.

The pattern is M:N: within every group of N contiguous elements, at most M are non-zero. Neuron supports 4:16, 4:12, 4:8, 2:8, 2:4, 1:4, and 1:2.

At 2:4, at least two entries in every group of four must be zero. One of the two matmul inputs needs to follow the pattern. Model weights are a common choice because they can be pruned ahead of time.

Why the pattern has to be structured#

A systolic array streams data through a fixed grid in lockstep. A dense matmul still processes arbitrary zeros. An M:N pattern lets the sparse path reserve a fixed number of slots per group and encode where those values belong.

To use a supported pattern, prune weights to meet the per-group limit and measure model accuracy. Fine-tuning can help recover accuracy after pruning. Both 1:2 and 4:8 keep at most half the weights, but a group of eight gives pruning more choice about which weights to keep. With 4:16, each group keeps at most a quarter of the weights.

Restrictions#

What is a tile?

A tile is a rectangular chunk of a tensor, sized to fit in on-chip memory and meet the shape limits of the instruction that will use it. Tensor instructions on a NeuronCore take tiles as inputs or destinations.

A typical NKI kernel loads tiles, computes on them and stores the results.

A tile in SBUF or PSUM has one partition dimension and one or more free dimensions. The first axis can use up to 128 physical partitions. The other axes describe the values within each partition.

# A BF16 moving tile for a matmul on NeuronCore-v3.
tile = nl.ndarray((128, 512), dtype=nl.bfloat16, buffer=nl.sbuf)

In a standard matmul, each input has a different role and a different limit on its free dimension.

Pipelining tiles#

A GPU can hide memory latency by running another warp while one waits for data. On Neuron, the kernel or compiler can overlap explicit DMA transfers with computation. With enough buffer space and independent work, a pipeline can look like this.

load tile n+1   (DMA, in background)
compute tile n  (Tensor Engine)
store tile n-1  (DMA, in background)

See latency hiding for how these transfers can overlap.

Tile size is also the main lever on arithmetic intensity in matmul. A larger tile can reuse its inputs for more operations per byte fetched from HBM.

←Structured sparsity→Tiling
/device-software/tiling

What is tiling?

Tiling is splitting a tensor operation into tile-sized pieces that fit the hardware's shape limits and on-chip memory. In an NKI kernel, split any axis that would otherwise need more than 128 on-chip partitions.

Matmul tile limits#

These limits apply to ordinary nc_matmul with hardware tiling mode off:

  1. Partition axis ≤ 128. SBUF has 128 partitions, wired to the 128 rows of the systolic array.
  2. stationary free axis ≤ 128, the number of array columns.
  3. moving free axis. On v2 and v3, the limit is 512 elements for an FP32 destination in one PSUM bank. On v4, the limit is 4,096 for FP32 output or 8,192 for BF16 output across eight banks. NKI nc_matmul reference, Trainium and Inferentia2 NKI architecture guide

In an unpacked matmul, the contraction dimension maps to the partition dimension of both operands.

That is the axis the array sums over. If a tile arrives with K on its free axis, move K to the partition axis before the matmul. You can arrange that layout in the operation that produces the tile or use a transpose.

Tiling a matmul#

For A[M, K] @ B[K, N], splitting an output axis and splitting the contraction axis do different things.

  • M and N split into independent tiles with disjoint outputs.
  • K splits into pieces whose results must be summed. Run the first nc_matmul with accumulate=False, then use accumulate=True to add later products to the same PSUM destination.

For example, unpacked K = 4096 can use 32 matmuls that accumulate into one PSUM tile, without a separate reduction.

Choosing sizes#

Larger matmul tiles can reuse inputs for more multiply-adds per byte of HBM traffic, increasing arithmetic intensity. A 128×128 stationary tile uses the full Tensor Engine array. On v4 a wider moving tile uses more PSUM banks, leaving less space for other live outputs.

Budget SBUF for all live tiles. Double-buffering needs room for the current tile and the next one so computation and data transfer can overlap. If the live tiles exceed capacity, the compiler may spill to HBM.

Layout decisions#

The free axis of the stationary tile becomes the partition axis of the result. The moving tile supplies the result's free axis. Choose stationary and moving roles that put the result in the layout the next operation needs.

Double-rate FP8 matmul requires the second axis of both inputs to have length 2. Zero-pad an odd contraction length before packing. MX matmul on v4 packs four contraction elements into each input element and requires a partition axis of size 32, 64, or 128. NKI nc_matmul_mx reference

What is nccom-test?

nccom-test measures how fast Trainium workers exchange data through collectives such as all-reduce, all-gather, reduce-scatter, and all-to-all. The example measures all-reduce across two workers (ranks) at several message sizes.

nccom-test -r 2 --minbytes 1024 --maxbytes 1073741824 --stepfactor 4 --datatype fp32 allr

Reading the results#

  • time(us) is the measured collective latency in microseconds.
  • algbw divides the message size by the measured time. It is the application's effective throughput for that operation and those ranks.
  • busbw scales algbw by a factor based on the collective and rank count. For an all-reduce across r ranks the factor is 2 × (r − 1) / r. It estimates communication bandwidth per rank from the amount of data the algorithm exchanges.

The columns labeled GB/s use GiB/s, according to the AWS guide. Compare runs with the same operation, message size, dtype and rank placement. --show-algorithm helps explain a change across configurations. AWS NCCOM-TEST user guide

Chip specifications describe the link hardware, while nccom-test reports the throughput of an operation. AWS inter-node collectives guide

What the compiler decides#

Neuron's device memory is software-managed. The compiler schedules compute, tiling, DMA transfers, buffer lifetimes, and synchronization. When the compiler sees several operations together, it can sometimes fuse them and keep intermediate results in on-chip memory. With native TorchNeuron, the compilation unit may be an operator in eager mode or a captured graph under torch.compile. The caller's graph and cache determine when a fresh compilation is needed.

Options worth knowing#

  • Precision. --auto-cast=none is the compiler default starting in Neuron SDK 2.27. Older versions defaulted to casting FP32 matrix operations to BF16. Use --auto-cast=matmult --auto-cast-type=bf16 to opt into that behavior. The framework's own mixed-precision policy is a separate setting. Neuron 2.27 compiler release notes
  • Model type and optimization level. --model-type can target transformer or unet-inference. -O controls the optimization level.
  • Integer behavior. --native-int64=enabled requests native 64-bit execution on Trn2 and later where supported. --implicit-integer-downcast controls whether operations without a suitable integer datapath can use a lossy conversion. Check data types and the CLI reference before relying on defaults.

When graph compilation fails, the framework decides how to handle the error. TorchNeuron has different fallback rules for eager operators and compiled graphs. The compilation caches can reuse a previously compiled executable.

The Neuron Persistent Cache saves compiled NEFFs from the legacy PyTorch/XLA and Transformers NeuronX stacks. When a later run needs the same executable, it can load the file and skip compilation. Native TorchNeuron and vLLM Neuron have their own caches with different settings.

Eager and compiled execution#

import torch

model = torch.nn.Linear(16, 8).to("neuron")
x = torch.ones(2, 16, device="neuron")
y = model(x)  # Eager
compiled = torch.compile(model, backend="neuron")
z = compiled(x)  # Compiles on the first call for this signature

Eager mode dispatches PyTorch operators as Python calls them. TorchNeuron translates a supported operator into StableHLO, compiles a device executable called a NEFF on a cache miss, and queues it on the device. Opt-in Adaptive Eager Execution can fuse eligible queued operations. By default, an unsupported eager operator can fall back to CPU with a warning, incurring synchronization and data transfers. AWS eager execution guide

torch.compile uses TorchDynamo to record related PyTorch operations as a graph in PyTorch's FX format. The Neuron backend lowers each captured graph through StableHLO and neuronx-cc to a NEFF. This lets the compiler optimize across operators. Graph breaks can split capture into separate graphs. If lowering or execution fails, the backend raises by default. You can enable a fallback that reruns the original graph in eager mode, where the eager operator fallback rules apply. Different input shapes can trigger recompilation. AWS compilation guide · Compilation caches

For large-model pretraining, TorchTitan Neuron provides tested recipes and a compiler-friendly SimpleFSDP option. Use NKI for a custom device kernel inside an otherwise standard PyTorch model. ←vLLM Omni Neuron→Arithmetic intensity
/perf/arithmetic-intensity

What is arithmetic intensity?

Arithmetic intensity measures how much math an operation does for each byte it moves. Choose the memory level you want to analyze, such as HBM, and count bytes crossing that boundary.

arithmetic intensity = FLOPs performed / bytes moved

Compare that number with the machine balance, the ratio of peak compute throughput to peak bandwidth for the same hardware scope. A Trainium2 chip has a published BF16 peak of 667 TFLOPS and HBM bandwidth of 2.9 TB/s, for a balance of about 230 FLOPs per byte. Use per-chip throughput with per-chip bandwidth. Several NeuronCores share a chip's HBM, so the bandwidth one core sustains depends on the workload and placement. Trainium2 specifications

In the roofline model, below the balance point bandwidth sets the upper bound. Above it, compute sets the upper bound. A real kernel can fall below both because of launch overhead, poor overlap, or limits on an individual engine.

OperationFLOPsIdeal BF16 bytes movedFLOPs per byte
Element-wise add, n elementsn6n (two reads, one write)0.17
Layer norm, n elements~5n4n (one read, one write)~1.3
Matmul, M×K by K×N2MKN2(MK + KN + MN)grows with operand reuse
Decode attention, one query per head, head width d, context length L~4dL (two matrix-vector products)~4dL (keys and values)~1

These are simplified examples. They omit bias and scale reads for layer norm, and omit softmax, queries and outputs for decode attention. Sharing keys and values across query heads also changes the decode estimate.

For a square matmul of size N that reads each input once and writes its output once, intensity is N/3. If the kernel rereads tiles from HBM, the real intensity is lower. Tiling increases reuse, and fusion can keep intermediate results in SBUF. In both cases, the same math requires fewer HBM transfers.

←XLA and HLO→Bank conflict
/perf/bank-conflict

What is a PSUM bank conflict?

A PSUM bank conflict occurs when two engines try to access the same bank of partial-sum memory at the same time and the accesses have to take turns.

On v2 through v4, PSUM holds 2 MiB across 128 partitions. Each partition contains eight banks of 2 KiB each. A bank holds 512 FP32 values.

Tile width by generation#

On NeuronCore-v3, one nc_matmul writes one PSUM bank per partition, giving a moving free-axis limit of 512 FP32 elements. On NeuronCore-v4, one destination can span all eight banks. The moving limit becomes 4,096 with FP32 output or 8,192 with BF16 output. The Tensor Engine still uses FP32 for internal accumulation. NKI nc_matmul reference

The conflict itself#

On NeuronCore-v2, the Vector and Scalar engines take turns accessing PSUM. On v3 they can access separate banks at full bandwidth in parallel. If both request bank 3 at the same time, one waits. Trainium2 NKI architecture guide

Banks and overlap#

On v3, separate banks allow the Tensor Engine to accumulate one output tile while another engine copies a completed tile to SBUF. On v4 a wider output can consume several banks, leaving less space for other accumulation groups. Little's Law explains why enough independent work has to be available to use that overlap.

A GPU shared-memory bank conflict also serializes accesses. There the contention is among threads in a warp. The v3 example here is contention between two engines.

←Arithmetic intensity→Batching
/perf/neuroncore-batching

What is NeuronCore batching?

Batching runs several inputs through a model together. A layer can reuse the same weights across inputs, doing more arithmetic for each byte loaded from HBM. This raises arithmetic intensity when weight reads dominate.

Batching during LLM decode#

At batch size one, an LLM may read the same weights for every token it generates. Processing more sequences in one step lets a kernel reuse those weights across sequences. The gain slows once compute or KV-cache traffic becomes the larger cost. The KV cache stores each sequence's past keys and values and grows with the number and length of sequences.

A larger batch can raise aggregate tokens per second while increasing queueing or per-step latency. A serving system chooses a batch size based on its throughput and latency targets.

Continuous batching#

In a fixed batch, a finished request's slot can sit idle while longer requests continue generating.

Continuous batching lets sequences join and leave a running batch between decode steps, so the scheduler can use freed slots for new requests. This is available in vLLM Neuron.

Batching and compilation#

NEFFs can be compiled for particular input shapes. A serving scheduler can vary which requests are in the batch and still select a compiled bucket for the shape it will run. For example, vLLM Neuron can bucket by the number of sequences and can optionally bucket by decode context length. Warming the relevant caches reduces cold start overhead. See the vLLM Neuron configuration reference.

In training#

Batching in training is a different question. There, batch size is a convergence parameter as much as a performance one, and it interacts with learning rate schedules. Batch size also changes the memory needed for activations.

←Bank conflict→Compute-bound
/perf/compute-bound

What does compute-bound mean?

An operation is compute-bound when the rate of arithmetic sets its runtime. For example, a well-tiled matrix multiplication can reuse its inputs enough to keep the Tensor Engine busy even though it only loads each input tile from device memory occasionally.

The roofline model predicts a compute limit when arithmetic intensity exceeds the machine balance. Use the peak for the engine doing the work and the bandwidth for the memory being accessed. Large matrix multiplications, convolutions, and long-prompt prefill can hit this limit when they reuse their inputs enough.

Prefill and decode have different reuse patterns#

LLM inference often shifts from compute-bound prefill to memory-bound decode. The actual bottleneck depends on the model, prompt length, context length, batch, and implementation.

PrefillDecode
WorkProcess prompt tokens, sometimes in chunksGenerate one token per sequence per step
Weight reuseAcross the prompt tokens in a chunkAcross sequences in the batch
Common bottleneckCompute on long promptsMemory at small batches
Helped byFaster matmul, sparsityQuantization, batching

With disaggregated inference, separate worker pools handle prefill and decode. The prefill worker passes the KV cache, which holds attention keys and values for the prompt, to the decode worker. The serving system can size each pool independently. See the vLLM Neuron disaggregation tutorial for supported configurations.

When arithmetic sets the limit#

  • Use a supported lower-precision format. FP8 matmul can reach about twice the per-engine BF16 peak on NeuronCore-v3. MXFP8 can reach about four times the per-engine BF16 peak on NeuronCore-v4.
  • Use structured sparsity if your model meets a supported zero pattern and your kernel selects the sparse matmul path. Speedups depend on generation and data type.
  • Check tile geometry. A kernel limited by arithmetic can still fall short of the published peak if it leaves part of the array idle.

Use Neuron Explorer to see which engine is busy. A normalization kernel can saturate the Vector Engine while leaving the Tensor Engine idle. The Tensor Engine's peak is then a poor baseline for that kernel.

←Batching→Data parallelism
/perf/data-parallelism

What is data parallelism on Neuron?DP

Data parallelism (DP) trains replicas of the same model on different examples from a batch. Each worker process (a rank) computes its own gradients. In PyTorch DistributedDataParallel (DDP), all-reduce synchronizes the gradients so every replica makes the same update.

DP can span instances in an UltraCluster. With ordinary DDP, each replica still needs room for its model, gradients, optimizer state, and activations. A mixed-precision Adam setup with BF16 parameters and gradients, FP32 master weights, and two FP32 moment buffers needs about 16 bytes per parameter before activations. For a 70B-parameter model that is roughly 1.1 TB per replica, well beyond the 96 GiB of one Trainium2 chip.

Sharding the replicated state#

ZeRO-1 shards the optimizer state across data-parallel ranks. It was available in legacy NxD Training.

For native Trainium training, TorchNeuron supports standard PyTorch DDP and FSDP2. The FSDP2 path in TorchTitan Neuron shards parameters, gradients, and optimizer state. It gathers parameters for computation and reduce-scatters the gradients. See the TorchTitan support matrix.

Overlapping the all-reduce#

DDP groups gradients into buckets and can start reducing a bucket as soon as its gradients are ready. Backpropagation can continue on layers whose gradients are still being computed. Neuron's dedicated collective communication cores can run those reductions alongside compute. The tail of the final collective still counts toward step time if backward finishes first. See latency hiding and nccom-test.

←Compute-bound→Engine parallelism
/perf/engine-parallelism

What is engine parallelism?

Engine parallelism means overlapping work on separate NeuronCore engines. Each engine has its own instruction stream. A matmul can run while another engine processes a result from a previous tile, provided the two operations have independent data to work on.

Here are the compute engines on NeuronCore-v3.

EnginePeak or configurationWork
Tensor79 BF16 TFLOPSmatmul, convolution
Vector1.0 FP32 TFLOPSreductions, normalization
Scalar1.2 FP32 TFLOPSactivations, exp
GpSimd8 × 512-bitgeneral-purpose SIMD operations

Plus the Sync Engine and DMA engines, which also run concurrently.

Overlapping tiles#

In a well-pipelined matmul chain, at any instant:

  • The Tensor Engine computes tile n into PSUM.
  • The Vector or Scalar Engine drains tile n-1 from PSUM to SBUF, applying the activation on the way.
  • DMA engines fetch tile n+1 from HBM.

Keeping several tiles in flight can hide the cost of loading inputs and copying completed results. Each stage still needs enough buffer space and memory bandwidth to keep pace.

Synchronization#

The compiler inserts hardware synchronization based on the dependencies it sees. When every step needs the full result of the previous one, the engines have to wait. Working in tiles can let one engine process tile n-1 as another computes tile n.

What limits it#

Some engine pairs contend for memory ports, and the rules changed between generations:

The Vector Engine's performance mode also shares a memory bus with GpSimd. Hardware arbitrates when they both request it. Trainium2 NKI architecture guide

Neuron Explorer shows a timeline per engine. Use it to see which work overlaps and where an engine sits idle. A core-level utilization figure from neuron-top cannot show that.

←Data parallelism→Fusion
/perf/fusion

What is operator fusion?

Fusion combines several operators into one so that intermediate results stay in on-chip memory instead of round-tripping to HBM.

Fusion can speed up memory-bound work by eliminating reads and writes at the boundary between operators.

Consider y = gelu(x @ w + b), unfused:

1. matmul:  read x and w from HBM  → write matmul result to HBM
2. bias:    read matmul result, b  → write biased result to HBM
3. gelu:    read biased result    → write y to HBM

The matmul and bias results each make a round trip through HBM. A fused version can keep both results on the chip:

1. read x, w, b from HBM into SBUF
2. matmul on the Tensor Engine     → PSUM
3. bias + gelu on Scalar/Vector    → SBUF
4. write y to HBM

The fused version does the same math with fewer HBM transfers, so its HBM arithmetic intensity is higher. Neuron's scratchpads are software-managed. The kernel or compiler must plan to reuse an intermediate on chip.

Fusion also maps naturally onto the hardware, because a NeuronCore's engines are specialized and independent. A fused matmul-plus-activation puts the matmul on the Tensor Engine and the activation on the Scalar Engine, where the Scalar Engine can process one tile while the Tensor Engine works on the next. That overlap is an example of engine parallelism.

Who does it#

neuronx-cc can fuse common patterns when the operators appear in the same compiled graph. You can also fuse them explicitly in an NKI kernel. FlashAttention, for example, computes attention in tiles and keeps intermediate scores on chip, avoiding a full attention matrix in HBM. NKI performance guide

The limit#

Fusion changes which buffers have to be live at the same time. If they exceed SBUF capacity, the compiled kernel may spill data back to HBM. Smaller tiles can help fit a fused operation, though they can also reduce reuse. Compare HBM traffic and execution time in Neuron Explorer.

←Engine parallelism→Latency hiding
/perf/latency-hiding

What is latency hiding on Neuron?

Latency hiding keeps an engine busy with independent work while another operation is in progress. For example, the Tensor Engine can compute one tile while a DMA engine loads the next.

The target shape is a software pipeline:

DMA:      load tile n+1 ────────────►
Tensor:   compute tile n ───────────►
DMA:      store tile n-1 ───────────►

This pipeline keeps the Tensor Engine busy if tile n+1 finishes loading into SBUF before compute needs it.

A GPU can switch to another ready warp while one waits for data. On Neuron, overlap between compute and data movement comes from the schedules produced by the compiler or from independent work you arrange in an NKI kernel.

The hardware that helps#

  • DMA engines run in parallel with compute. 128 of them on Trainium2, about 16 per NeuronCore-v3.
  • The Sync Engine exists to trigger DMAs without injecting instructions into a compute engine's stream.
  • The DGE generates descriptors independently. This can reduce the work the issuing engine spends preparing a transfer.
  • CC-Cores do the same for collectives, overlapping communication with computation.

What you do#

Expose independent work. Use Python range() for statically unrolled tile loops in current NKI. Organize loads and compute so there is independent work for the scheduler to overlap. Use nl.fori_loop or nl.while_loop for device-side loops when the bounds depend on runtime values. See nki.language and the NKI optimization guide.

Double-buffer. Size tiles so that two fit in SBUF alongside the other live data. One buffer feeds compute while DMA fills the other.

Watch the profile. Gaps on the Tensor Engine timeline in Neuron Explorer, with DMA activity in the gaps, can indicate that loads are on the critical path.

Overlapping collectives#

The same idea applies to distributed training. Gradient buckets can be reduced as they become ready while the rest of the backward pass continues. How much time this saves depends on when the communication starts and when the result is needed. See data parallelism.

←Fusion→Little's Law
/perf/littles-law

What is Little's Law?

Little's Law relates how much work is in a system to how fast work completes and how long each item spends there. In steady state:

average work in flight = throughput × average time in the system

To plan a pipeline, use the target throughput and an estimate of latency to size the work in flight. The required concurrency can be higher once transfers queue or compete for bandwidth. Neuron's compiler or NKI kernel has to expose enough independent work for the engines to overlap.

DMA example#

Suppose a DMA transfer from HBM to SBUF takes 2 μs on average and the throughput target is 2 TB/s across a chip. In this example, you need about 4 MB of data in flight across the chip. For equal transfers of 256 KiB, that is about 16 outstanding transfers.

A Trainium2 chip provides 128 DMA engines for local and cross-device transfers. If a kernel loads one tile, waits, computes, and then issues the next load, the transfers never overlap even if spare DMA engines are available. Trainium2 NKI architecture guide

Tensor Engine example#

The Tensor Engine is deeply pipelined, so several LoadStationary/MultiplyMoving pairs are in flight at once. This is why AWS advises reasoning about a matmul's initiation interval rather than the end-to-end latency of a single instruction — the latency is already hidden, provided you supply enough independent work.

PSUM has eight banks per partition. On NeuronCore-v3, each nc_matmul output fits within one bank, leaving the other banks for independent accumulation groups. On NeuronCore-v4, a wide output can span all eight banks. The room available for interleaving accumulation groups depends on output width and data type.

Using it#

In a profile, look for gaps between engine instructions or long periods spent waiting for dependencies. To increase useful work in flight:

  • Double-buffer. Use one tile buffer for compute while DMA fills the other.
  • Expose independent work. Use separate buffers for transfers and computation that can overlap. In NKI 0.7, small loops with known bounds can use Python range and unroll at specialization time. NKI loop guide
  • Leave PSUM banks free. A wide accumulation group can occupy all eight banks, leaving no bank for a second group.

This term is the Neuron counterpart of Little's Law in Modal's GPU Glossary, where the same law explains warp occupancy instead of pipeline depth.

←Latency hiding→Memory-bound
/perf/memory-bound

What does memory-bound mean?

An operation is memory-bound when the rate of data transfer sets its runtime. Element-wise operations often fall into this category because they read and write many values for a small amount of arithmetic.

In the roofline model, this is the region where bandwidth caps throughput. Which memory matters depends on where the data moves. An operation can be limited by HBM or by a path into an on-chip scratchpad.

LLM decoding at batch size one#

In a batch-1 dense decode step, a weight streamed from HBM typically contributes one multiply-accumulate. BF16 stores it in two bytes, so the weight-only arithmetic intensity is roughly 1 FLOP per byte. KV-cache reads and other traffic also take bandwidth.

If each step reads all the weights from HBM, this gives a weight-only upper bound at batch size one.

tokens/sec ≤ HBM bandwidth / bytes of model weights

An 8B model in BF16 has about 16 GB of weights, which fit in a Trainium2 chip's 96 GiB of HBM. With the full chip bandwidth of 2.9 TB/s, the weight-only ceiling is about 180 tokens/s. That estimate excludes KV-cache traffic, compute, and communication. See the Trn2 architecture specifications.

What actually helps#

Quantize. Storing weights in fewer bytes can raise the bandwidth ceiling. Actual savings depend on the format, scale metadata, and which weights are quantized. See FP8 and MX formats.

Batch. Reading the weights once and using them for many sequences amortizes the traffic, raising intensity roughly linearly with batch size. This is the idea behind batching.

Fuse. Keep intermediates in SBUF rather than round-tripping them to HBM between operators.

Use more chips. Tensor parallelism can read shards in parallel across physical chips. Effective bandwidth depends on rank placement, shard balance, and communication overhead.

Reuse tiles. Tiling can reduce how often the same inputs cross the HBM boundary. Leave enough scratchpad space for both the tile and the rest of the pipeline.

A faster Tensor Engine helps only if arithmetic is taking time on the critical path. Measure the relevant bytes and bandwidth before tuning matmul throughput.

←Little's Law→Model FLOPs utilization
/perf/mfu

What is model FLOPs utilization?MFU

Model FLOPs utilization (MFU) compares the rate of useful model arithmetic with the hardware's theoretical peak rate.

MFU = useful model FLOPs per second / peak FLOPs per second

For dense transformer training, a common starting estimate of useful work is 6 × parameter count × token count per step. The approximation captures the main weight-matrix operations. The exact count depends on the architecture, sequence length, and which weights are active. Padding and activation recomputation add hardware work without increasing the model FLOPs in that estimate.

Compare runs using the same counting convention. Report the device count, precision, and which portion of the run you timed. For small-batch LLM decode, weight or KV-cache traffic can dominate. Pair MFU with tokens per second and measured HBM bandwidth utilization to see where time goes. Neuron Explorer metric definitions

On Neuron this needs care, because "peak" depends on precision:

Raising it#

The levers are the ones in this section, and which applies depends on the roofline:

  • Engine parallelism — overlap independent work on the engines your kernel uses.
  • Latency hiding — overlap DMA with compute.
  • Fusion — remove HBM round trips.
  • Tile geometry — fill the Tensor Engine array while leaving enough scratchpad space to overlap work.
  • Overlapped collectives — launch gradient reductions as buckets become ready.

A profile in Neuron Explorer can show whether the job spends time on arithmetic, transfers, or waiting for other ranks.

What is NeuronCore Pipeline?

NeuronCore Pipeline is an Inf1 inference feature. The compiler splits a model into consecutive groups of layers. Each group runs on a NeuronCore with its weights held in on-chip memory, and requests pass from one group to the next.

Keeping the weights on chip avoids fetching them from device DRAM for every request. NeuronLink-v1 carries activations when stages span devices. An inf1.24xlarge has 16 Inferentia chips and 64 NeuronCores. AWS gives BERT and ResNet-50 as examples that can benefit without large batches.

The legacy neuron-cc compiler enables it with:

--neuroncore-pipeline-cores N

Benchmark core counts that fit the model and compare throughput and latency. See the AWS NeuronCore Pipeline reference.

Modern Trainium serving typically stores weights in HBM and stages smaller tiles through SBUF. Tensor parallelism splits the work inside a layer. Pipeline parallelism also splits by layer and can run with weights in device memory.

←Model FLOPs utilization→Overhead
/perf/overhead

What is overhead on Neuron?

Overhead is time and work spent preparing or dispatching computation. On Neuron, it includes host dispatch, first-use compilation, synchronization, and transfers. A profile separates these from time spent compute-bound or memory-bound on the device.

Dispatch, compilation, and graph breaks#

Eager dispatch. TorchNeuron can dispatch an ATen operator at a time. A new operator specialization can trigger compilation before it executes. Unsupported eager operators may run on the CPU, adding device transfers and synchronization. Experimental adaptive eager mode can fuse eligible queued operations. It is off by default in Neuron 2.33.

Compiled execution. torch.compile(backend="neuron") lets the compiler compile each captured graph as a NEFF. This gives the compiler room to fuse operators and schedule their data transfers, with fewer host dispatches. Dynamo graph breaks split the work into separately compiled segments. Legacy PyTorch NeuronX lazy execution has a separate mechanism for materializing pending work.

Cold or repeated compilation. A new shape, dtype, compiler setting, or failed graph guard can require a new specialization. A guard is a condition PyTorch checks before reusing a captured graph. Check cache hits and account for warmup separately when measuring steady state. Serving stacks often use fixed buckets for this reason.

Transfers and synchronization#

Host-to-device movement. Moving inputs from host DRAM to device HBM can stall a job whose data pipeline cannot keep up. Use neuron-ls to check device and NUMA placement. Printing an eager device tensor also incurs a synchronization and host copy.

Collectives on the critical path. Reducing gradients after backward adds the uncovered collective time to each step. Neuron's dedicated CC-Cores can communicate while compute engines work when dependencies allow it. See latency hiding.

Neuron Explorer correlates device and system activity. Look at host dispatch and compilation around device idle gaps, as well as DMA and collectives before a stalled compute engine.

See AWS's TorchNeuron compile guide and eager execution overview.

←Overhead→Pipeline parallelism
/perf/pipeline-parallelism

What is pipeline parallelism on Neuron?PP

Pipeline parallelism (PP) assigns different groups of layers to different devices. Each group is a stage. Stages send activations forward and gradients backward during training. A stage can also use tensor parallelism to split its layer computations across devices.

The pipeline bubble#

A stage waits for the previous stage to produce its input. Splitting a batch into smaller microbatches lets stage 1 begin the next one while stage 2 works on the current one. The bubble is time that stages spend idle while the pipeline fills, drains, or waits for a slower stage.

For one fill-and-drain pass with equally fast stages, the idle fraction is (stages - 1) / (microbatches + stages - 1). More microbatches can reduce this overhead, though scheduling and activation memory still matter. In autoregressive inference, each sequence's next token depends on its last token. Serving multiple independent sequences provides more work to pipeline.

Combining strategies#

A training job can combine several strategies. The communication pattern helps decide where to place each group.

What is the roofline model?

The roofline model estimates the speed an operation could reach given the available compute throughput and memory bandwidth. Plot arithmetic intensity on the x-axis and FLOPs per second on the y-axis.

throughput ceiling = min(peak compute throughput,
                         arithmetic intensity × peak memory bandwidth)

The slanted part of the chart is the bandwidth limit. The flat part is the compute limit. The two meet at the machine balance.

Numbers for Trainium2#

For a Trainium2 chip against HBM at 2.9 TB/s:

PrecisionPeakMachine balance
BF16667 TFLOPS~230 FLOPs/byte
FP81,299 TFLOPS~448 FLOPs/byte
FP32181 TFLOPS~62 FLOPs/byte

At a given precision, the lower of the two ceilings predicts the bottleneck if the operation can reach that ceiling. Switching to FP8 raises the compute ceiling. It can also change the operation's intensity, since it can take fewer bytes to store the inputs. Trainium2 published chip peaks

Choose the relevant rates#

Pick the peak for the engine doing the work. On NeuronCore-v3, the Tensor Engine peaks at 79 BF16 TFLOPS. The Vector Engine peaks at 1.0 FP32 TFLOPS. A reduction running on the Vector Engine has a different ceiling from a Tensor Engine matmul.

Pick the bandwidth for the data path you measured. A kernel that works in SBUF after loading its inputs has a different bandwidth limit from one that continually fetches from HBM. See peak rate.

Using it#

Measure the achieved throughput, estimate the intensity for the chosen data path, and plot the point.

  • Near the slanted line: reduce bytes moved with tiling, fusion, or quantization.
  • Near the flat line: look for ways to do less work or use a faster supported format.
  • Below either limit: profile the operation in Neuron Explorer. Idle engine time can come from poor overlap, synchronization, or unexpected spills.

What is spilling on Neuron?

Spilling moves a value out of fast memory to make room for other work. A reload brings it back when the kernel needs it. The Neuron compiler can insert these transfers, such as saving an intermediate from SBUF to HBM and reading it back.

The program still computes the same result, but the extra transfers may show up as unexpected DMA activity. In Neuron Explorer, compare Spill Save Bytes and Spill Reload Bytes with overall SBUF traffic. NKI guide to spill metrics

The Tensor Engine writes its results to PSUM. Copy completed results to SBUF so the next matmul has space to accumulate.

Reducing spills#

Count all buffers that must fit at once. If you double-buffer inputs to overlap loads and compute, each input needs two buffers. Fusion can avoid HBM traffic between operators, but the fused operation may also need space for more live intermediates. Adjust the tile size and compare the profile again.

What is tensor parallelism on Neuron?TP

Tensor parallelism (TP) splits computations within a layer across several logical NeuronCores. Each rank (worker process) computes on its slice of the weights. A collective combines or redistributes the results.

For example, a feed-forward block's first linear layer can be column-parallel, giving each rank a slice of the output features. A row-parallel second layer consumes the sharded features and produces partial outputs. An all-reduce combines them when every rank needs the full result. With sequence parallelism, a reduce-scatter can leave the result sharded. Attention commonly shards by head.

What TP buys#

TP can fit a model whose weights and KV cache exceed the memory of one chip. Spreading weight shards across chips also lets those chips read their local HBM in parallel. The bandwidth gain depends on the physical chips used, the balance of the shards, and the cost of the collectives between ranks.

On a Trn2 instance with LNC=2, each chip has four logical cores. A TP group of 16 ranks can occupy four chips if placement uses four ranks per chip. Check the device map to see which chips supply bandwidth.

Choosing the degree and placing ranks#

  1. Count the available logical cores with Logical NeuronCore configuration and the device allocation in mind. A full trn2.48xlarge exposes 64 logical cores at LNC=2.
  2. Check model and backend constraints. The number of attention heads, KV heads, and intermediate dimensions can constrain valid sharding. Some implementations replicate KV heads at higher TP degrees.
  3. Benchmark valid degrees that fit the model and KV cache. More ranks give each rank less work and add communication. In vLLM Neuron, TP trades off with other strategies such as data parallelism.
  4. Keep frequently communicating ranks in a fast NeuronLink domain where possible. A Trn2 UltraServer links instance members over NeuronLink, and a Trn3 UltraServer uses NeuronSwitch and direct links inside its scale-up domain. Neuron DRA can allocate topology-aware groups on eligible EKS clusters.

See AWS's vLLM Neuron tensor parallelism design for worked examples of attention, MLP sharding, and KV-head replication.
